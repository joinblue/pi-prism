### 2.2 雙腦對抗失敗根因與快取/配額邊界真相

- `[FACT]` **重型推理模型 (`550b` / `deepseek-v4.1` / `120b`) 思維鏈耗時特性**：在多輪漸進式迴圈 (`Multi-Turn Loop`) 的中間回合，重型推理模型需先生成完整 `<think>` 區塊才會產出最終文字；原先固定 `22s` 逾時與 `maxTokens: 768` 會在思維鏈完成前觸發 `AbortSignal.timeout`，導致假性 `Request was aborted`。
- `[FACT]` **自适应逾時與 Token 預算放寬**：`model-router.ts` 已針對重型推理模型將中間回合逾時放寬至 `35s`（最終回合 `48s`），並將中間回合 `maxTokens` 提升至 `1536`，確保 `<think>` 推理不被腰斬。
- `[FACT]` **獨立無狀態 `ping` 對 Prefix KV Cache 之真實影響**：供應商端之 Prefix KV Cache 係以 Token 序列雜湊樹 (Radix Tree) 進行匹配；只要預檢請求採用獨立無狀態短訊息且**不寫入主對話 Session `.jsonl`、不變更主腦預設 API Key (`pool[0]`)、不改動 `messages[0]` 系統提示詞**，單次 1-token `ping` 絕不會沖刷或污染主對話的 Prefix KV Cache。
- `[INFERRED]` **主動高頻預檢之真正破口在於 40 RPM 滑動視窗**：雖然無狀態 `ping` 不影響 KV Cache，但在 NVIDIA 40 RPM 限制下，任何定時全模型輪詢都會擠壓雙腦協同 (`architect` + `challenger` 多輪迴圈) 的可用 RPM 配額，甚至觸發供應商反濫用節流。
- `[HYPOTHESIS]` 當同一時段多個不同模型系列同時出現 `HTTP 504 Gateway Timeout` 而無 `429` 時，代表供應商區域推理叢集瞬時擁塞，此時在同一供應商內切換第 2 把 API Key 無效，必須透過被動斷路器切換至輕量模型（如 `lightning-30b` 或 `glm-5.3-flash`）或跨供應商 (`google-vertex`) 備援。

## 三、下一步行動：三層式零配額損耗健康治理架構

- `[FACT]` **第一層：執行期被動斷路器 (Runtime Passive Circuit Breaker — 已實作於 `model-router.ts`)**
  1. **永久除名 (`HTTP 410 Gone / 404 Not Found`)**：一旦任何候選模型在 `dispatch_specialist` 中回傳 `410` 或 `404`，立即將該模型加入 `DEPRECATED_404_MODELS` 與永久冷卻表，本 Session 後續調度 0 秒直接跳過，不再重試。
  2. **15 分鐘降級冷卻 (`HTTP 504 / Timeout Abort`)**：當某候選模型發生閘道超時或連線中斷，自動將該模型排入 `RUNTIME_COOLDOWN_UNTIL_MS`（冷卻 15 分鐘），後續 `dispatch_specialist` 優先選用順位健康的備援模型；僅在所有候選模型皆處於冷卻時才保底重試。
  3. **原地指數退避 (`HTTP 429 Rate Limit`)**：遇 `429` 時保留當前 Sticky Key 原地等待 `5s -> 10s` 恢復 RPM 滑動視窗，保護已建立之多輪 KV Cache。
- `[INFERRED]` **第二層：按需單點預檢與手動診斷 (On-Demand Single-Target Probe)**
  - 禁止背景高頻全量輪詢；僅在使用者手動執行診斷或切換未知模型時，才針對單一目標模型發送 `max_tokens=1` 測試。
- `[INFERRED]` **第三層：模型庫同步與外部神諭驗證**
  - 定期或於遇到 `410` 時比對 `.Friday/models-store.json` 與 `.Friday/models.json`，確保 `.Friday/role-models.json` 綁定之所有角色模型 100% 存在於 `.Friday/models.json` 活躍白名單中，並透過 `python3 schemas/schema_validator.py --run-oracle` 與 `python3 scripts/test_friday_architecture.py` 驗證。
